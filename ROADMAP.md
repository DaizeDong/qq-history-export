# Roadmap

Current: **v0.1.0**

## v0.1.0 (current)

- Pull a selected classic mobile QQ SQLite candidate from an already rooted Android device or emulator. The pull checks snapshot stability and schema, creates and removes a temporary device copy, and leaves account ownership unverified until key recovery (`tools/qq_pull.py`).
- Observe already-decoded messages in the running client's Java heap with Frida 16.x. Match message identities to encrypted rows, recover the repeating XOR field key, and verify it using at least two distinct known plaintext messages, each covering two complete key periods. The evidence bundle binds the key and decoded account checks to the selected database snapshot (`tools/qq_keyfind.py`, `tools/qq_evidence.py`).
- Detect variable key periods from 1 through 64 bytes when the known messages provide sufficient evidence. The implementation selects the smallest period that explains the complete known pair; it does not assume a fifteen-byte key (`tools/qq_field_cipher.py`).
- Decode short and long messages offline into JSONL, one object per exported text message. Export requires complete (100%) UTF-8 decoding coverage of nonempty `msgData` fields on `-1000` rows in supported `mr_friend_<md5>_New` and `mr_troop_<md5>_New` tables. Key and account evidence is checked separately; coverage alone cannot establish key correctness. Invalid selected text aborts the export and preserves any existing output (`tools/qq_decode.py`).
- Keep pulled databases, key/evidence bundles, and exports in a verified private companion repository, outside the public tool repository. Public examples and fixtures are synthetic and generated by `tools/make_fixtures.py`.

## Validation and scope limits

- Synthetic fixtures and offline checks do not establish compatibility with a particular real QQ client, Frida build, or Android device. Real-device/client acceptance remains pending for this candidate.
- Coverage describes the selected supported text fields in one local snapshot. It does not establish whole-account history completeness, recover missing or unsynchronized history, or cover unsupported tables and message types. Whitespace-only messages retain their exact text in JSONL, and every selected timestamp is validated before promotion.
- The current schema targets classic pre-NT mobile QQ. QQ NT and richer message types remain outside the supported export scope.

## Planned

- HTML output alongside JSONL, organized by conversation.
- An offline key recovery path using the database alone, without observing the running client.
- Richer message types beyond plain text: images, replies, forwarded cards, and other non-text content.
